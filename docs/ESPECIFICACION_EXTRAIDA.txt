del servidor de chat
Arquitectura, API, E2EE, PostgreSQL, Redis, WebSocket, invitaciones, votaciones y recuperación
Versión consolidada de producción v1 · Especificación normativa para implementación, pruebas y operación
Estado: ESPECIFICACIÓN DE PRODUCCIÓN v1. Este documento sustituye las versiones anteriores y cierra las decisiones de arquitectura, autenticación, contratos REST/WebSocket, consistencia, configuración, pruebas, despliegue, observabilidad y operación del MVP.


1. Objetivo y alcance
Definir de forma única e implementable un servicio de chat independiente que pueda integrarse con la aplicación principal. El servidor gestiona identidad, sesiones, conversaciones, invitaciones, entrega en tiempo real, persistencia opcional de ciphertext, metadatos técnicos, votaciones y recuperación de claves entre dispositivos.
MVP: conversaciones 1 a 1, con modelo de datos preparado para grupos futuros.
Transporte: WebSocket para todos los mensajes, ACK y eventos de entrega.
Gestión: REST para cuenta, sesiones, conversaciones, invitaciones, historial persistente, votaciones, Web Push y transferencia temporal de claves.
Cifrado: extremo a extremo. El servidor no necesita descifrar el contenido.
Modos: stored/persistente hasta 30 días y ephemeral/efímero sin historial de contenido en servidor.
Sin contraseñas: la cuenta usa sesiones/tokens y una frase de recuperación BIP-39 de 24 palabras como mecanismo de recuperación.

4.2 Frase de recuperación BIP-39 de 24 palabras
1.  Al crear la cuenta se genera una frase BIP-39 de 24 palabras (256 bits de entropía antes del checksum) mediante una fuente criptográficamente segura.
2.  La frase se muestra al usuario una sola vez.
3.  El servidor conserva únicamente memory_hash usando Argon2id; nunca conserva la frase original.
4.  La recuperación verifica email + frase, revoca las sesiones anteriores y emite nuevas credenciales.
4.3 Entrada desde la aplicación principal
La aplicación principal puede emitir un token temporal firmado para abrir el chat sin un segundo login. El Chat API verifica firma, audiencia, expiración y usuario; después emite su propia sesión.

POST /auth/exchange

Chat API
  ├─ access token: 24 h

4.4 Flujo desde invitación
Un usuario que llega mediante un código de invitación puede completar el registro si todavía no tiene cuenta. Tras el registro/verificación recibe una sesión normal y continúa con el flujo de invitación.
5. Cifrado extremo a extremo y claves
El requisito funcional es: A cifra localmente, el servidor transporta o conserva ciphertext, B descifra localmente. Las claves privadas permanecen bajo control de los clientes.
Usuario A
  └─ cifra localmente
        ↓
Servidor: solo ciphertext
        ↓
Usuario B
  └─ descifra localmente
Protocolo E2EE del MVP: libsodium con un único par de claves Curve25519/X25519 por usuario. El cliente cifra y descifra localmente mediante crypto_box_easy/crypto_box_open_easy. Cada mensaje usa un nonce aleatorio único de 24 bytes. El formato lógico de metadatos criptográficos es: protocol_version + nonce + sender_public_key. En la API protocol_version viaja como entero; crypto_meta es un blob binario obligatorio de 56 bytes: nonce[24] || sender_public_key[32], transportado como Base64URL. PostgreSQL conserva únicamente la clave pública vigente. La clave privada permanece en el cliente; durante un cambio de dispositivo solo se sube un blob ya cifrado con TTL máximo de 24 horas y el secreto viaja por QR. El servidor no necesita interpretar el ciphertext para entregarlo.
5.1 Claves públicas
El servidor almacena una única clave pública vigente por usuario, necesaria para que otros clientes puedan cifrar mensajes destinados a él.
La clave privada no se almacena de forma permanente en PostgreSQL ni en ningún almacenamiento durable del servidor.
user_keys contiene una sola fila por usuario. Rotar la clave sustituye la clave pública vigente; las claves privadas antiguas que el usuario quiera conservar son responsabilidad del cliente.
5.2 Transferencia temporal de claves entre dispositivos
Cuando el usuario cambia de dispositivo puede transferir su bundle privado usando ambos dispositivos simultáneamente. El servidor solo conserva un blob ya cifrado y nunca recibe el secreto de descifrado.
1.  El dispositivo nuevo inicia una transferencia y obtiene transfer_id.
2.  El dispositivo antiguo genera un secreto aleatorio de transferencia y cifra localmente el bundle de claves.
3.  El blob cifrado se sube al servidor asociado a transfer_id.
4.  El secreto se transmite directamente al dispositivo nuevo mediante QR.
5.  El QR puede incluir transfer_id, secret y protocol_version. El secret no se envía al servidor.
6.  El dispositivo nuevo descarga el blob, lo descifra localmente y confirma la transferencia.
7.  El servidor elimina el blob tras confirmación o automáticamente al cumplirse 24 horas.
Dispositivo viejo ── blob cifrado ──► Servidor (TTL 24 h)
      │                                  │
      └──── QR: secreto ───────────────► Dispositivo nuevo
                                         │
                               descarga + descifra localmente
5.3 Recuperación del historial desde el otro participante
Si A pierde dispositivo/claves locales pero B conserva su historial local, B puede reenviar a A una copia ordenada de la conversación, cifrada de nuevo para las nuevas claves de A. Este proceso no requiere que el servidor conozca el contenido. Se transporta como un flujo de recuperación efímero por WebSocket para evitar crear duplicados persistentes.
B descifra localmente su copia histórica.
B vuelve a cifrar cada elemento para las nuevas claves de A.
B conserva el orden original y, opcionalmente, marcas temporales originales dentro del payload cifrado.
El servidor solo retransmite frames recovery.replay.* y no los incorpora a messages.
Si ambos participantes pierden sus dispositivos/claves y no existe una copia recuperable, el historial queda perdido definitivamente.
6. Modos de conversación
6.1 Modo stored / persistente
1.  A cifra el mensaje localmente y lo envía por WebSocket.
2.  FastAPI registra metadatos de contacto y almacena el ciphertext en PostgreSQL.
3.  El receptor puede recuperar el ciphertext durante el periodo de conservación.
4.  Cada ciphertext expira como máximo 30 días después de sent_at.
5.  El receptor envía ACK por WebSocket; el estado de entrega se actualiza.
6.2 Modo ephemeral / efímero
1.  A cifra el mensaje localmente y mantiene el ciphertext exclusivamente en su dispositivo; todavía no lo envía al servidor.
2.  A envía message.offer al servidor con message_id y metadatos mínimos, pero sin ciphertext. El servidor crea una oferta temporal con EPHEMERAL_OFFER_TIMEOUT_SECONDS=60 por defecto.
3.  El servidor comunica message.offer a B. Si B no está conectado, puede enviar Web Push genérico para que se conecte. Si B no responde dentro de 60 segundos, la oferta expira y A recibe message.failed.
4.  Cuando B está preparado, responde message.ready al servidor; el servidor retransmite message.ready a A. Solo a partir de ese momento A puede enviar el ciphertext.
5.  A envía message.send con el mismo message_id. El servidor guarda el ciphertext únicamente en Redis/RAM durante la entrega y lo reenvía a B como message.new.
6.  B envía message.ack únicamente después de recibir el ciphertext completo. El servidor elimina primero el ciphertext temporal y después notifica a A mediante message.delivered.
7.  Si B se desconecta durante la entrega antes del ACK, el servidor elimina el ciphertext y envía message.failed a A. El modo ephemeral no deja historial de contenido en el servidor; para reintentar tras un fallo definitivo el cliente crea un nuevo message_id.
6.3 Cambio de ephemeral a stored
El modo inicial lo determina el código que utiliza el guest para contactar con el host: el host dispone de una variante ephemeral y otra stored de su invitación.
Una conversación ephemeral puede convertirse a stored únicamente por el host/huésped, es decir, el usuario creador del código de invitación. Una conversación stored no puede volver a ephemeral.
El cambio a stored es efectivo desde el momento de la actualización. Solo los mensajes enviados después del cambio se almacenan en PostgreSQL; el historial efímero anterior permanece únicamente en los clientes.
Al producirse el cambio, los demás participantes reciben conversation.mode_changed y pueden continuar o abandonar la conversación. Si abandonan, pueden eliminar su copia local del chat.
Metadatos: Aunque el contenido efímero no persiste, se mantiene durante 30 días el registro técnico mínimo de contacto definido en message_events/message_deliveries.
7. Invitaciones y apertura de conversaciones
Cada usuario dispone de una identidad de invitación activa y permanente. A partir de ella el servidor genera dos códigos: uno para iniciar chats ephemeral y otro para iniciar chats stored. Ambos permanecen válidos hasta que el usuario pulsa “Regenerar código”.
Roles del MVP: host (huésped) es el creador/propietario del código y receptor de la solicitud; guest (invitado) es el usuario que canjea el código para iniciar el contacto. Solo el host puede aceptar una conversación pending y ejecutar el cambio irreversible ephemeral → stored. Cualquier participante puede cerrar o abandonar según las reglas generales.
1.  invitation_id es un UUID aleatorio generado mediante CSPRNG y no contiene información derivable del user_id. PostgreSQL mantiene la relación invitation_id → creator_user_id.
2.  El payload binario tiene formato fijo y todos los enteros multibyte se codifican big-endian: version:uint8 (1 byte) || invitation_id:UUID (16 bytes, orden de red) || generation:uint32 (4 bytes) || created_at:uint64 (8 bytes, Unix epoch en segundos UTC) || mode:uint8 (1 byte; 0 = ephemeral, 1 = stored). El payload ocupa 30 bytes y no contiene user_id ni nick.
3.  El servidor calcula HMAC-SHA-256(INVITATION_HMAC_SECRET, payload), concatena payload || MAC[32] y codifica los 62 bytes resultantes como Base64URL sin padding. El código resultante tiene 83 caracteres. No se usa bit de paridad ni conversión directa de bytes a caracteres UTF-8.
4.  Al canjear un código, el servidor decodifica Base64URL, verifica el HMAC en tiempo constante, valida invitation_id/generation/status y crea una conversación pending con el mode incluido en el código.
5.  Antes de que el host acepte, el guest conoce únicamente la identidad técnica de invitación; no ve el nick ni información pública del host. El host sí sabe que existe una solicitud asociada a su código y decide si acepta la conversación.
6.  Se permiten hasta 5 mensajes de gracia. Tras alcanzar el límite no se pueden enviar más mensajes hasta que el host acepte la conversación.
7.  Regenerar revoca la identidad de invitación activa y crea una nueva generation/invitation_id; todos los códigos anteriores dejan de ser válidos. Cada 6 meses el cliente muestra un recordatorio opcional para recomendar la regeneración, sin hacerlo automáticamente.
8. Mensajes de gracia y votación genérica
La lógica de votación debe ser reutilizable en grupos futuros. La primera política implementada es majority_absolute.
approved ⇔ yes_votes > eligible_members / 2

La votación retain_grace_messages se abre automáticamente cuando el host acepta la conversación y dura exactamente 30 segundos.
eligible_members se congela al abrir la votación y votes.expires_at = created_at + 30 segundos.
Mientras la votación está abierta, la interfaz de conversación queda bloqueada y el servidor rechaza nuevos message.offer y message.send para esa conversación.
Cada usuario con derecho a voto puede emitir como máximo un voto. Al cumplirse el plazo, cualquier usuario que no haya votado se computa implícitamente como NO.
Al cerrar la votación se aplica majority_absolute: approved si yes_votes > eligible_members / 2; en caso contrario rejected. En stored el resultado conserva o elimina los mensajes de gracia; en ephemeral se comunica a los clientes para que lo apliquen localmente.
9. Cierre y reapertura
Cualquier participante puede cerrar unilateralmente la conversación.
El cierre bloquea de inmediato nuevos message.offer y message.send.
El otro participante puede conservar o eliminar su historial local.
Una conversación closed no se reactiva.
Para volver a contactar se vuelve a introducir un código de invitación válido y se crea un nuevo flujo pending.

  ↓ message.offer / Web Push genérico
B
  ↓ message.ready
Servidor
  ↓ message.ready

  ↓ message.send (ciphertext)

  ↓ recepción completa

  "request_id": "uuid",

10.4 Idempotencia y reintentos
message_id es generado por el cliente y representa un único mensaje lógico. El servidor lo trata como clave idempotente global: recibir de nuevo el mismo message_id no crea otra fila, no incrementa de nuevo grace_messages_used y no genera una segunda entrega independiente. Si el mensaje ya está pending, delivered o failed, el servidor devuelve/notifica su estado actual. Si llega el mismo message_id con conversation_id, sender o contenido criptográfico incompatibles, responde system.error con MESSAGE_ID_CONFLICT. Tras un fallo definitivo, un reintento funcional debe usar un nuevo message_id.

12. Web Push
Web Push es el canal inicial de notificaciones. En stored se dispara cuando el servidor acepta un nuevo message.send destinado al usuario. En ephemeral puede dispararse al recibir message.offer si B no está conectado, para darle la oportunidad de conectarse y responder dentro del timeout de 60 segundos.
El payload es genérico y no contiene el texto ni el ciphertext del chat. Puede incluir event_type, conversation_id y message_id para que el cliente abra/actualice la conversación o responda a una oferta ephemeral.
La suscripción se asocia al usuario y puede renovarse o revocarse.
Aunque el MVP no ofrece multi-dispositivo normal, el modelo de tabla puede admitir varias suscripciones para evolución futura.

15.1 Entrega efímera
1. A → servidor: message.offer(message_id), sin ciphertext.
2. SET ephemeral:offer:{message_id}:{recipient_id} ... EX 60.
3. Si B está online: PUBLISH message.offer. Si está offline: enviar Web Push genérico y esperar conexión/ready hasta timeout.
4. B → servidor: message.ready(message_id).
5. Servidor → A: message.ready; DEL ephemeral:offer:...
6. A → servidor: message.send con ciphertext + crypto_meta.
7. Crear message_events/message_deliveries en PostgreSQL de forma idempotente.
8. SET ephemeral:delivery:{message_id}:{recipient_id} <ciphertext> EX 60.
9. PUBLISH events:user:{recipient_id} message.new.
10. B recibe el ciphertext completo y envía message.ack.
11. UPDATE message_deliveries = delivered.
12. DEL ephemeral:delivery:{message_id}:{recipient_id}.
13. Servidor → A: message.delivered.

Si offer expira sin message.ready:
  DEL ephemeral:offer:...
  message.failed → A
  no crear message_events y el ciphertext nunca sale de A

Si B se desconecta después de message.send y antes del ACK:
  DEL ephemeral:delivery:...
  UPDATE delivery = failed
  message.failed → A

-- Contenido stored expirado
DELETE FROM messages
WHERE content_expires_at <= now();

-- Metadatos técnicos de contacto > 30 días
DELETE FROM message_events
WHERE expires_at <= now();

-- Sesiones
DELETE FROM auth_sessions
WHERE expires_at <= now()
   OR (revoked_at IS NOT NULL AND revoked_at < now() - interval '30 days');

19. Reglas de implementación
No aceptar contraseñas ni crear password_hash.
No insertar ciphertext ephemeral en messages.
Crear message_events/message_deliveries tanto para stored como para ephemeral para conservar únicamente la trazabilidad técnica de 30 días.
Antes de insertar en messages, verificar conversations.mode = stored.
content_expires_at no puede superar sent_at + 30 días.
El contador grace_messages_used se incrementa de forma transaccional.
Una conversación pending con 5 mensajes de gracia consumidos bloquea nuevos envíos hasta aceptación.
Aceptar la conversación (acción exclusiva del host) crea inmediatamente la votación retain_grace_messages con expires_at = created_at + 30 segundos. Mientras esté open, message.offer y message.send se bloquean para esa conversación; los usuarios sin voto al vencer el plazo cuentan como NO.
Una conversación closed no acepta mensajes.
Solo se permite el cambio de mode ephemeral → stored. El cambio inverso se rechaza.
Al convertir a stored, únicamente los mensajes enviados después de mode_changed_at se insertan en messages. Los demás participantes reciben conversation.mode_changed y pueden abandonar el chat.
Regenerar invitación revoca la activa anterior y crea un nuevo invitation_id/generation dentro de la misma transacción. Los dos códigos (ephemeral/stored) se derivan con HMAC y no se guardan completos.
message.send/message.ack solo por WebSocket.
Los frames recovery.replay.* se transportan efímeramente y no se guardan como mensajes normales.
key_transfer:{id} contiene solo blob cifrado; el secreto viaja por QR y no debe registrarse en logs.
INVITATION_HMAC_SECRET debe generarse criptográficamente, mantenerse estable y fuera de la base de datos. Conocer el algoritmo o invitation_id no permite fabricar un código válido sin este secreto.
GET /invitations/me genera bajo demanda las dos variantes Base64URL de la invitación activa. Cada 6 meses el cliente puede mostrar un recordatorio de rotación, sin regeneración automática.
Redis debe iniciar con persistencia desactivada.
MAX_MESSAGE_LENGTH=256 debe ser configurable. Añadir además un límite máximo de bytes del envelope cifrado.
crypto_meta v1 es obligatorio y tiene exactamente 56 bytes: nonce libsodium de 24 bytes seguido de sender_public_key Curve25519 de 32 bytes. protocol_version se almacena por separado.
message_id es idempotente. Un duplicado compatible devuelve el estado existente sin insertar otra fila, sin incrementar contadores y sin duplicar entrega. Un duplicado incompatible devuelve MESSAGE_ID_CONFLICT. Tras un fallo definitivo, un nuevo intento usa un nuevo message_id.
En conversaciones creadas por invitación, el creador del código se registra como role=host y quien canjea el código como role=guest. Solo host puede POST /conversations/{id}/accept y POST /conversations/{id}/upgrade.
El token de invitación v1 usa el layout fijo version:uint8 || invitation_id[16] || generation:uint32 || created_at:uint64 || mode:uint8, todos los enteros multibyte big-endian; después se añade HMAC-SHA-256 y se codifica Base64URL sin padding.
El modo ephemeral usa obligatoriamente handshake message.offer → message.ready → message.send → message.new → message.ack → message.delivered. El ciphertext no abandona A antes de ready.
EPHEMERAL_OFFER_TIMEOUT_SECONDS=60 y EPHEMERAL_DELIVERY_TIMEOUT_SECONDS=60 son valores iniciales configurables. Si offer vence, no se crea message_event. Si B se desconecta durante delivery, se elimina el ciphertext y el estado pasa a failed.
En Web Push, stored notifica al aceptar message.send; ephemeral notifica message.offer cuando B no está conectado. Nunca se incluye texto ni ciphertext.

21. Fuera de alcance de producción v1
Chats grupales operativos. El esquema está preparado, pero el MVP es 1 a 1.
Multi-dispositivo permanente. Solo se admite coexistencia temporal durante transferencia de claves.
Imágenes y archivos adjuntos.
Políticas de votación distintas de majority_absolute, aunque el modelo las contempla.
Bindings concretos de libsodium según la plataforma cliente final (web/móvil/escritorio), manteniendo Curve25519/X25519 y el mismo formato de claves.
Integración definitiva con la lógica de negocio del marketplace más allá del bootstrap de sesión.
22. Criterios de aceptación del MVP
Registro sin contraseña y recuperación con 24 palabras BIP-39.
Access token de 24 h y refresh token rotatorio.
Entrada desde la app principal mediante token firmado.
WebSocket autenticado con envelope genérico y soporte de message.offer/ready/send/new/ack/delivered/failed.
stored conserva ciphertext hasta 30 días y permite recuperarlo.
ephemeral ejecuta handshake offer/ready, mantiene el ciphertext en A hasta ready, espera offer 60 s por defecto, no deja ciphertext persistente y elimina/falla si B se desconecta antes del ACK.
Metadatos técnicos de contacto se purgan a los 30 días.
Una identidad de invitación active por usuario, dos códigos derivados (ephemeral/stored), HMAC-SHA-256 + Base64URL, regeneración manual y recordatorio semestral opcional.
Máximo 5 mensajes de gracia y votación majority_absolute bloqueante durante 30 segundos; ausencia de voto = NO.
Cierre unilateral y reapertura solo mediante nuevo flujo de invitación.
Cambio irreversible ephemeral → stored funcional; solo persiste mensajes posteriores al cambio y el otro participante puede abandonar la conversación.
Web Push funcional sin incluir contenido del mensaje.
Transferencia de claves mediante blob cifrado + secreto por QR, TTL máximo 24 h.
Redis reiniciable sin persistir mensajes efímeros ni blobs de claves.
message_id es idempotente y las retransmisiones no crean duplicados ni consumen dos veces el límite de mensajes de gracia.
Cada conversación creada por código identifica un único host y un guest; solo host puede aceptar pending y ejecutar ephemeral → stored.
Los códigos de invitación usan layout binario fijo big-endian + HMAC-SHA-256 + Base64URL sin padding.
crypto_meta de cada mensaje contiene nonce[24] || sender_public_key[32] y protocol_version se conserva explícitamente.

23.4 Paginación
GET /conversations y GET /conversations/{id}/messages usan cursor opaco, no números de página.
?limit=50&cursor=<base64url>

{
  "items": [],
  "next_cursor": null
}
limit por defecto: 50. Mínimo: 1. Máximo: 100.
El cursor se construye con la clave estable de orden y el UUID de desempate, se codifica Base64URL sin padding y siempre se trata como entrada no confiable.
Conversaciones: orden updated_at DESC, id DESC.
Mensajes stored: orden sent_at DESC, id DESC. El cliente puede invertir cada página para presentarla cronológicamente.
Un cursor inválido devuelve 400 INVALID_CURSOR. No se firma porque no concede permisos; el servidor valida todos sus campos.
24. Autenticación, sesiones y recuperación de producción
24.1 Access token JWT
Los access tokens son JWT firmados con Ed25519/EdDSA. El Chat API posee la clave privada de firma; consumidores que solo necesiten verificar reciben únicamente claves públicas.
Header:
{
  "alg": "EdDSA",
  "typ": "JWT",
  "kid": "chat-2026-H2"
}

Claims:
{
  "sub": "user-uuid",
  "sid": "session-uuid",
  "iss": "chat-api",
  "aud": "chat-client",
  "iat": 1789490000,
  "nbf": 1789490000,
  "exp": 1789576400,
  "jti": "uuid"
}
TTL: 24 horas (86400 s).
No se incluyen nick, email, roles de conversación ni otros datos mutables.
Se rechaza cualquier alg distinto de EdDSA, typ inesperado, kid desconocido, issuer/audience incorrectos o token fuera de tiempo.
Tolerancia máxima de reloj para iat/nbf/exp: 30 segundos. El host de producción debe mantener sincronización NTP.
Cada petición autenticada comprueba además que sid existe, no está revocado y no ha expirado. El JWT no es suficiente por sí solo.
Logout revoca sid inmediatamente. La revocación se publica por Redis para cerrar WebSockets asociados a esa sesión.
24.2 Refresh token
Token opaco de 32 bytes generado mediante CSPRNG y transportado como Base64URL sin padding.
TTL: 30 días.
El servidor nunca almacena el token en claro; almacena SHA-256(token) como 32 bytes.
Cada uso rota el token. El token utilizado queda marcado used_at y se emite uno nuevo en la misma token_family_id.
Si vuelve a aparecer un token con used_at no nulo, se considera reutilización: se revoca inmediatamente toda la familia y la respuesta es REFRESH_REUSE_DETECTED.
Un reintento de red del cliente debe usar únicamente la respuesta del primer refresh exitoso; no se tolera volver a presentar el token anterior.
24.3 Persistencia de refresh para detectar reutilización
Para que la detección sobreviva reinicios de Redis, producción añade historial persistente de refresh tokens. auth_sessions continúa representando la sesión/sid; auth_refresh_tokens conserva únicamente hashes y estados.
CREATE TABLE auth_refresh_tokens (
  token_hash BYTEA PRIMARY KEY CHECK (octet_length(token_hash) = 32),
  session_id UUID NOT NULL REFERENCES auth_sessions(id) ON DELETE CASCADE,
  token_family_id UUID NOT NULL,
  issued_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at TIMESTAMPTZ NOT NULL,
  used_at TIMESTAMPTZ NULL,
  revoked_at TIMESTAMPTZ NULL
);
CREATE INDEX idx_auth_refresh_tokens_session
  ON auth_refresh_tokens(session_id, expires_at);
CREATE INDEX idx_auth_refresh_tokens_family
  ON auth_refresh_tokens(token_family_id);
auth_sessions.refresh_token_hash puede mantenerse como puntero al refresh vigente para acceso rápido, pero la decisión de reutilización se toma contra auth_refresh_tokens.
24.4 Bootstrap desde la aplicación principal
El bootstrap token también es JWT Ed25519/EdDSA, pero usa un par de claves diferente al del Chat API. La aplicación principal conserva la privada; Chat API conserva únicamente las públicas de verificación.
{
  "sub": "user-uuid",
  "iss": "main-app",
  "aud": "chat-api",
  "iat": 1789490000,
  "nbf": 1789490000,
  "exp": 1789490300,
  "jti": "uuid"
}
TTL máximo admitido: 5 minutos. Un token con exp-iat superior a 300 s se rechaza.
jti es de un solo uso. POST /auth/exchange realiza una operación atómica SET NX en Redis con TTL hasta exp; un jti ya consumido se rechaza.
Si Redis no está disponible, /auth/exchange falla con 503. No existe degradación que permita replay.
No se incluyen nick, email ni permisos. sub debe corresponder a una cuenta de chat existente.
24.5 Frase de recuperación y Argon2id
BIP-39 de 24 palabras; wordlist inglesa para protocol_version=1.
Antes de verificar/hash: normalización Unicode NFKD y separación canónica mediante un único espacio ASCII.
Argon2id: memory_cost=65536 KiB (64 MiB), time_cost=3, parallelism=1, salt aleatorio=16 bytes, hash=32 bytes.
Se almacena la cadena codificada completa de Argon2id con parámetros y salt; nunca la frase.
POST /auth/recover correcto revoca todas las sesiones actuales del usuario y crea una nueva sesión.
La recuperación de cuenta no recupera una clave E2EE privada perdida. El historial cifrado solo puede recuperarse por las reglas de transferencia/replay ya definidas.
24.6 Verificación de email
Token de 32 bytes CSPRNG, Base64URL sin padding.
Solo se persiste SHA-256(token). TTL: 30 minutos. Un token es de un solo uso.
Solicitar reenvío invalida tokens anteriores aún no usados y genera uno nuevo.
Registro emite una sesión normal con email_verified=false; cuenta, recuperación y verificación funcionan, pero crear/canjear invitaciones, obtener ws-ticket y enviar mensajes exige email_verified=true.
24.7 Rotación de claves de firma
Las claves Ed25519 de access token y las claves Ed25519 de bootstrap son pares independientes.
Rotación ordinaria cada 6 meses. kid identifica la clave.
Solo una clave privada firma en cada momento. Claves públicas anteriores se conservan exclusivamente para verificación hasta que expire el último token que pudieron firmar.
Una clave privada comprometida se retira de verificación inmediatamente. Para una clave de Chat JWT comprometida se revocan sesiones y se fuerza nueva autenticación.
INVITATION_HMAC_SECRET no rota por calendario: rotarlo invalida todas las invitaciones y solo se hace por compromiso o migración planificada.
VAPID tampoco rota por calendario porque obligaría a renovar suscripciones Push; se rota ante compromiso.

25.6 Visibilidad durante pending
Mientras status=pending, peer=null para ambos clientes. La UI trabaja con role host/guest y conversation_id, no con la identidad pública del otro participante.
El guest recibe la clave pública vigente del host al canjear el código para poder cifrar mensajes de gracia.
El host puede recibir/descifrar gracia con su clave, pero la identidad pública del guest no se expone hasta accept.
Tras accept, ambos obtienen UserPublic del peer mediante GET /conversations/{id}.
26. Contrato WebSocket v1
26.1 Autenticación mediante ticket de un solo uso
No se coloca el access token JWT en la URL WebSocket. El cliente obtiene primero un ws-ticket mediante REST y lo usa una sola vez:
POST /api/v1/auth/ws-ticket
Authorization: Bearer <access JWT>

→ 201 {"ticket":"...", "expires_at":"..."}

wss://chat.example/ws/v1?ticket=<ticket>
ticket: 32 bytes CSPRNG, Base64URL sin padding.
Redis guarda ws_ticket:{sha256(ticket)} → {user_id,sid} con TTL 30 s.
La apertura WebSocket usa GETDEL/operación atómica equivalente; ticket consumido o expirado no puede reutilizarse.
Si la sesión sid se revoca, Redis Pub/Sub ordena cerrar cualquier socket asociado inmediatamente.
Redis no disponible implica fallo cerrado: no se emiten tickets nuevos y no se aceptan conexiones sin validación.
26.2 Conexión, heartbeat y reconexión
Tras autenticación el servidor envía session.ready con user_id, sid, server_time y heartbeat_interval_seconds=25.
Heartbeat usa frames WebSocket nativos ping/pong, no mensajes JSON personalizados.
El servidor envía ping cada 25 s y considera muerta una conexión que no responde durante 75 s. presence TTL es 90 s renovable.
Cliente reconecta con backoff 1, 2, 4, 8, 16, 30 s y jitter aleatorio de hasta 20 %. Cada reconexión exige un ws-ticket nuevo.
Al reconectar, el cliente consulta por REST el estado de mensajes dudosos mediante /messages/{id}/status y recupera historial stored si procede.
26.3 Envelope normativo
{
  "type": "message.send",
  "request_id": "uuid",
  "conversation_id": "uuid-or-null",
  "timestamp": "2026-09-15T18:30:00Z",
  "payload": {}
}
type, request_id, timestamp y payload son obligatorios. conversation_id es null únicamente para eventos de sesión sin conversación.
request_id identifica la operación/frame y message_id identifica el mensaje lógico; no son intercambiables.
Para eventos correlacionados, el servidor conserva request_id cuando resulte útil. Para eventos espontáneos genera uno nuevo.
En frames cliente→servidor, timestamp se valida como RFC3339 pero no es autoritativo. En frames servidor→cliente, timestamp es hora del servidor.
payload siempre es un objeto JSON. Frames binarios se rechazan con close 1003.

26.5 Reglas de entrega stored
stored no usa message.offer/message.ready. El cliente envía message.send directamente.
El servidor crea message_events/messages/message_deliveries en una transacción y confirma aceptación al emisor mediante el estado del mensaje. Si el receptor está conectado, también emite message.new.
Si el receptor está offline, el mensaje permanece pending y se envía Web Push genérico. Al volver, el cliente recupera el ciphertext mediante GET /conversations/{id}/messages.
ACK actualiza delivered, pero no borra messages; el ciphertext permanece hasta content_expires_at.
26.6 Reglas de entrega ephemeral y carreras con cambios de estado
message.offer snapshottea únicamente sender/conversation/recipient y no crea message_events.
message.send obtiene lock de la conversación antes de crear el evento. Si la conversación ya cambió a stored, se rechaza el envío ephemeral con message.failed y el cliente reintenta como stored con un message_id nuevo.
POST /upgrade, POST /accept y DELETE /conversation también bloquean la fila de conversación. El orden real de commit determina si un send ocurrió antes o después del cambio.
Al hacer upgrade se cancelan offers ephemeral todavía no convertidos en message.send. Un delivery que ya creó message_event antes del upgrade puede terminar normalmente como ephemeral.
Al cerrar una conversación se cancelan offers pendientes y se rechazan nuevos sends. Un message.send ya confirmado antes del cierre puede completar su ACK.

appendonly no
save ""

Redis no usa volumen persistente para datos del chat. Se recomienda tmpfs para /data si la imagen/entorno lo necesita.

28. Consistencia, concurrencia y retención
28.1 Bloqueos y transacciones
Operaciones que cambian status/mode/grace_messages_used ejecutan SELECT ... FOR UPDATE sobre conversations dentro de una transacción.
accept, upgrade, close, leave y creación de message_event se serializan respecto a la misma conversación para impedir carreras de modo/estado.
El incremento de grace_messages_used y la creación del message_event forman parte de la misma transacción. Un retry idempotente no vuelve a incrementar el contador.
La creación de ballot usa PRIMARY KEY(vote_id,user_id). Repetir la misma choice devuelve el estado existente; una choice diferente después del primer voto devuelve 409.
Al votar, el servidor comprueba expires_at contra reloj del servidor aunque el scheduler todavía no haya cerrado formalmente la votación.
28.2 Fingerprint para idempotencia de message_id
Para detectar MESSAGE_ID_CONFLICT incluso después de borrar ciphertext ephemeral, message_events añade un fingerprint no reversible del payload cifrado.
payload_fingerprint = SHA-256(
  protocol_version_be32 || crypto_meta_raw || ciphertext_raw
)
ALTER TABLE message_events
  ADD COLUMN payload_fingerprint BYTEA NULL
  CHECK (payload_fingerprint IS NULL OR octet_length(payload_fingerprint) = 32);
Todo message.send nuevo en producción escribe payload_fingerprint.
Duplicado con mismo message_id, conversation_id, sender_id y fingerprint devuelve el estado existente y no repite efectos.
Duplicado con cualquiera de esos campos diferente devuelve MESSAGE_ID_CONFLICT.
La garantía de deduplicación del servidor dura mientras exista message_events (30 días). El cliente debe tratar UUIDv4 message_id como globalmente no reutilizable para siempre.
28.3 Retención y limpieza
Consultas de historial excluyen de forma inmediata cualquier row con content_expires_at<=now(), aunque el worker físico todavía no la haya borrado.
Worker de limpieza se ejecuta al menos una vez por minuto. Objetivo operativo: lag de purga física <5 minutos; alertar si supera 5 minutos.
message_events/message_deliveries se purgan a los 30 días. auth_refresh_tokens expiran con la familia y se eliminan después de 30 días adicionales de auditoría técnica del reuse, sin contener tokens en claro.
email_verification_tokens se borran al usarse o expirar.
Redis TTL elimina offers, deliveries, ws-tickets y key transfers automáticamente; el código también hace DEL inmediato en éxito/cancelación.
28.4 Consistencia tras fallo de proceso
Si una instancia cae durante delivery ephemeral, Redis conserva como máximo el TTL restante. El receptor pierde el socket y no puede ACK; el delivery termina failed/expired.
Un reconciliador marca message_deliveries pending de ephemeral como failed cuando ya no existe la clave ephemeral:delivery y ha vencido el timeout.
El emisor que perdió la conexión consulta /messages/{id}/status. Si el estado es failed/expired crea un message_id nuevo para reintentar.
En stored, PostgreSQL es autoritativo: si message_events+messages committearon, el mensaje existe aunque el WebSocket se cierre antes de la respuesta al emisor; el retry con el mismo message_id recupera el estado sin duplicar.
29. Plan de pruebas y puertas de calidad
29.1 Unitarias obligatorias
Serialización/deserialización Base64URL y layout big-endian exacto de invitaciones; HMAC válido, inválido, truncado y version desconocida.
JWT EdDSA: kid, iss, aud, iat/nbf/exp, alg substitution y sesión revocada.
Refresh rotation y reuse detection de toda la token_family_id.
Argon2id + normalización NFKD de BIP-39.
majority_absolute para 2/3/5/10 miembros y ausencia de voto=NO.
Transiciones de conversación y prohibición stored→ephemeral.
Idempotencia de message_id y MESSAGE_ID_CONFLICT por fingerprint.
Límites de gracia, permisos host/guest y visibilidad pending.
Expiración de offer/delivery/key transfer/ws-ticket.
29.2 Integración obligatoria
FastAPI + PostgreSQL + Redis reales en contenedores de test.
Flujo register→verify→keys→invitation→redeem→grace→accept→vote.
Ephemeral completo offer→ready→send→new→ack→DEL Redis→delivered.
Ephemeral con B offline, timeout de offer, desconexión entre send y ack y caída de proceso.
Stored online y offline con recuperación por REST y limpieza por expiry.
Upgrade concurrente con offers/sends; cierre concurrente con send; grace_message_limit bajo concurrencia.
ws-ticket one-time, expirado, reutilizado y sid revocado con cierre del socket.
Transferencia de claves: upload/download/delete/TTL y tamaño máximo.
Web Push generado sin texto/ciphertext.
29.3 Seguridad y robustez
Fuzzing de invitation token, cursores, Base64URL, JWT y envelopes JSON.
Rechazo de frames binarios, payload sobredimensionado, campos extra, UUID inválido y protocol_version desconocido.
Comprobación automática de que logs no contienen access/refresh/bootstrap tokens, recovery mnemonic, ciphertext, crypto_meta, invite code completo ni secretos.
Pruebas de rate limiting y fail-closed cuando Redis no está disponible.
Pruebas de autorización horizontal: un usuario no puede leer conversación, voto, status, key transfer o clave de otro sin relación permitida.

30. Despliegue, observabilidad y recuperación operativa
30.1 Topología de producción inicial
Docker Compose en un host Ubuntu Server. Solo Caddy publica 80/443; FastAPI, PostgreSQL y Redis permanecen en red interna Docker.
Puerto 80 solo redirige a HTTPS. Producción acepta REST por HTTPS y WebSocket por WSS.
FastAPI y Caddy se ejecutan sin privilegios innecesarios. PostgreSQL usa volumen persistente; Redis no usa almacenamiento persistente.
Firewall del host permite únicamente administración necesaria y 80/443 públicos. PostgreSQL/Redis no se exponen a Internet.
Imágenes y dependencias se fijan a versiones concretas; las actualizaciones pasan por CI antes de despliegue.
30.2 Migraciones y despliegue
Alembic es la herramienta de migración de referencia para FastAPI/Python.
La migración se ejecuta una sola vez antes de levantar la nueva versión de aplicación. Si falla, no se arranca la versión nueva.
Cambios destructivos se dividen en dos releases cuando sea necesario: primero compatibilidad, después eliminación.
En SIGTERM la instancia marca readiness=false, deja de aceptar ws-tickets/nuevos sockets, permite hasta 15 s a entregas en vuelo y después cierra sockets con 1001. Redis TTL/reconciliación resuelven los pendientes restantes.
Rollback preferido: volver a la imagen anterior siempre que el esquema siga siendo backward-compatible; no se hace downgrade destructivo automático de la BD.
30.3 Logs y métricas
Logs estructurados JSON a stdout con timestamp, level, service, request_id, endpoint/event_type, status/error_code y IDs técnicos necesarios.
Nunca registrar: access/refresh/bootstrap token, recovery mnemonic, private keys, secrets, invite code completo, verification token, ciphertext, crypto_meta ni key-transfer blob.
Retención inicial de logs: 14 días.
Métricas Prometheus internas: latencia/errores REST, conexiones WS activas, offers/ready/delivered/failed, timeouts, Redis memory, PostgreSQL pool, cleanup lag, refresh reuse detections y Web Push failures.
Las métricas no llevan nick, email ni contenido de mensajes como labels.

30.5 Backups compatibles con la retención del chat
Para no conservar ciphertext temporal más allá de su política, producción realiza backup lógico únicamente de datos durables. El contenido de mensajes y otros datos TTL no entran en copias de larga duración.
Backup de datos durables cada 6 horas, cifrado, con 7 días de snapshots frecuentes y 4 snapshots semanales.
Incluir: users, user_keys (solo públicas), invitations, conversations, conversation_members y esquema/migraciones. web_push_subscriptions puede incluirse si el backup está cifrado.
Excluir datos de backup durable: messages, message_events, message_deliveries, auth_sessions, auth_refresh_tokens, email_verification_tokens, votes y vote_ballots.
Consecuencia aceptada: ante pérdida total de PostgreSQL, el historial stored temporal puede perderse y todos los usuarios deben reautenticarse. Se prioriza la semántica de retención y simplicidad sobre respaldar contenido temporal.
Prueba de restauración al menos una vez al mes. Objetivo de recuperación de metadatos durables: RPO <=6 h y RTO <=2 h en el despliegue inicial.
30.6 Health y mantenimiento
/health/live no consulta dependencias; evita reinicios en cascada por una caída externa.
/health/ready comprueba una query mínima PostgreSQL y PING Redis con timeout corto. Si falla, Caddy/orquestación no debe enviar tráfico nuevo a esa instancia.
Tareas programadas: cleanup de expirados cada minuto, cierre de votos vencidos, reconciliación de deliveries ephemeral y limpieza de sesiones/tokens.
El reloj del host se sincroniza por NTP. Una deriva >2 s debe generar aviso porque afecta expiraciones y validación JWT.
30.7 Caddy y superficie pública
TLS automático de Caddy; solo TLS moderno permitido por configuración por defecto actualizada.
HSTS: Strict-Transport-Security: max-age=31536000 en el dominio dedicado del chat.
CORS: únicamente ALLOWED_ORIGINS explícitos; no wildcard en producción.
Límite de body HTTP 128 KiB y timeouts razonables a nivel proxy; WebSocket upgrade permitido solo en /ws/v1.
No se publican PostgreSQL, Redis, /metrics ni documentación interactiva.
